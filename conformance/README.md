# Conformance

This folder holds the `sanning.agent/1` suite: 635 cases, one directory each, under [`cases/`](cases/). Each case pins the reading of [`agent-events.md`](../specs/agent-events.md) section 10 on one record and the records held beside it, and what an SDK signs, refuses and sends. [`../scripts/read.mjs`](../scripts/read.mjs) reads every case, and `npm test` checks that it does. The suite runs offline.

Every file under `cases/` is generated by [`../scripts/generate.mjs`](../scripts/generate.mjs). Do not edit a case by hand: change the generator and run `npm run generate`.

## One case

Each case is one directory, `cases/<group>/<name>/`:

| File | Always | What it holds |
|---|---|---|
| `record.json` | yes | The record under test, as a verifier holds it after the envelope layer: `{"event_id", "public_key", "record"}`. `record` is the event record; `event_id` and `public_key` are its envelope's. |
| `held.json` | no | The other records the verifier holds beside it, in the same shape, for step 7 (`agent-events.md` section 10). A set: two entries with the same `event_id`, key and record are one record. Absent: the record is read on its own, steps 1 to 6. Present and empty: the verifier holds nothing else. |
| `expected.json` | yes | The reading. |
| `sent.json` | no | On the mode cases only: the fields of `record` Sanning receives in the record's `data_mode`, as `{"record"}`, plus `"content"` in `full` (`agent-events.md` section 7). The fields, not the request that carries them. |
| `content.json`, `content.bin`, `message.json` | one, on every `valid` case | What the record commits to: the content object, the bytes of a file that was read, or a hand-off's message. See below. |
| `README.md` | yes | One line: what the case is about. |

`expected.json`:

| Member | Meaning |
|---|---|
| `valid` | `true` when the record on its own passes steps 1 to 6, or is outside this vocabulary and carries no salt in the wrong form: an SDK signs it. `false`: an SDK refuses to sign it. |
| `verdict` | `verified`, `failed`, `incomplete`, or `null` for a record outside this vocabulary. Read with `held.json` where present. A `failed` reading of this layer has the reason kind `nonconforming`. |
| `reason` | The first reason of the verdict, when the verdict is not `verified`. A pairing failure can give `failed` with `valid: true`: the record alone is well formed, and the record it names is not its start. |
| `at` | A JSON Pointer into `record` for the field `reason` is about. |
| `reasons` | Every reason, when the verdict is not `verified`, each as `{"reason", "at"}`, in the order steps 1 to 7 give them. Steps 1 to 6 stop at the first failure, so most cases have one; step 7 runs every sub-step and can give several. The first is `reason` and `at`. |
| `findings` | Findings, in the order step 6 then steps 7a to 7j produce them, whatever the verdict. |

A case that fails at step 4 fails on exactly one schema error, except the cases in `precedence`, which fail on at least two and pin which one is reported (`agent-events.md` section 10.1). Its reason is the same in any JSON Schema validator that tests a `pattern` as ECMA-262's `RegExp.prototype.test` does: a search in which the pattern carries its own anchors, `$` the end of the string with no exception for a final newline, and `[0-9]` the ASCII digits. A validator in another regular expression dialect translates each pattern (`agent-events.md` section 4.1): in Python, `re.search` with `re.ASCII` and a final `$` written `\Z`. Without the translation it reads `rules/id-trailing-newline` and `rules/version-non-ascii-digit` differently; with `re.fullmatch` it reads `rules/event-ref-data-uri` differently.

## What a `valid` case commits to

Every `valid` case carries one file holding what its record's hash commits to, so an SDK can be tested on hash agreement:

| File | On | Hashed as |
|---|---|---|
| `content.json` | every type but the hand-offs, and a file that could not be read | SHA-256 of the JCS bytes of the parsed object: `event.content_hash`. |
| `content.bin` | `agent.file-required-only`, a file that was read | SHA-256 of the file's bytes as they are, so `sha256sum content.bin` is `event.content_hash` (`agent-events.md` section 5.9). |
| `message.json` | the four hand-off cases | SHA-256 of the JCS bytes of the parsed message: `event.message_hash`, compared in either case (`agent-events.md` section 8.2). |

`content.json` holds the content object of a `valid` case: the framework's object for a type a framework step produces, and the fixed object of `agent-events.md` section 5 for `agent.run_opened`, `agent.run_closed`, `agent.approval.resolved`, `agent.decision`, `agent.custom` and `agent.error`. Its hash is SHA-256 over the RFC 8785 (JCS) bytes of the parsed object, never over the file's bytes, which are pretty-printed: `event.content_hash` is that hash, and `event.content_length`, where the record carries it, is the number of those bytes. Where the record has `context.content_scrubbed: true`, `content.json` is the object after the credential scrub of section 9.3, so scrubbing it again changes nothing.

An SDK hashes each file as it hashes what it is handed, and agrees with the record. A file that could not be read commits to `{}`, which `agent.file-every-field` carries in `content.json`. `message.json` is the message as JSON; `event.message_bytes_hash` on the `every-field` hand-offs commits to bytes as they crossed, which a pretty-printed file is not, and nothing grades it. The mode cases `data-mode/full` and `data-mode/full-file` carry their content in `sent.json`.

## The groups

| Group | What it covers |
|---|---|
| `valid` | Every type, with only its required fields and with every field. |
| `pairing` | Every start with its end, read from both sides; a step that occurred, which is no operation; an end that fails, with step 7 run to the end; a start with no end; ends that name the wrong record; several candidates in either order; a decoy under another key; a record held twice; records that do not verify; halves that disagree; keys in upper case; an approval answered in a later run. |
| `end-only` | An end whose start the adapter cannot observe, with and without the declaration. |
| `precedence` | Records that fail in several places: which reason and pointer are reported, in step 4 and across the rules of step 5. |
| `run-closed` | A closing record read with the records it lists, all of them or part, every listed record not held reported, and step 7 run to the end. |
| `seq` | Two records at one position of one invocation, and the records that are not. |
| `refusal` | A tool call end read beside its approval's answer: `completed`, `failed`, `interrupted` or `skipped`, after `rejected`, `responded`, `approved` or `edited`, under its own key or another, in this invocation or a later one, and after an escalation. |
| `salt` | The record salt: missing on each of the 19 agent types, present in a wrong form on each of the seven other types, and present or absent on a plain `event` record. |
| `incomplete` | A run that may be incomplete: a gap in `run.seq` before the record, a record before it that does not verify, and a promised closing record not held. |
| `unknown-field` | An unknown member at every object in every type's record. |
| `missing-field` | Each required member missing, once per field path. |
| `event-type` | The closed set: unknown, builder-defined and misspelled types; a record outside the vocabulary. |
| `event-schema` | The version: missing, every invalid spelling (a trailing newline and a non-ASCII digit included), unknown major, unknown minor, a type a later version adds. |
| `data-mode` | A tool call in each mode and a file record in `standard` and `full`, with what Sanning receives; a mode that does not exist, two modes in one invocation and under two keys. |
| `disclosure` | Revealed and hidden fields, listed and not, a revealed `null`, and a custom record's value and name. |
| `handoff` | The unchecked-parts count and list, the part-count inequalities, and the counts across a pair, a finding that moves no verdict. |
| `rules` | The other rules: a step that occurred and the operation fields it never carries, the salt's form on an agent record, `skipped`, `responded`, custom names, plumbing, interrupts, closing count and reason, file reason, the capture list, the first record, scrubbing, the chain key of a linked record, ids and fixed formats Sanning receives in `private`, how a pattern is tested, the event section. |

The keys in these cases are 64 hex characters derived from a label, not curve points, and no case carries a signature: this layer reads records after the envelope layer has verified them.
